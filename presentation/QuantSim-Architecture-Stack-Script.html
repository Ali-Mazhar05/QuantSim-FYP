Opening

This is the QuantSim architecture in a single view. It reads top to bottom, five layers, and a request only ever travels in one direction through them. The thing worth watching as we go down is not how many boxes there are — it is which boxes are permitted to talk to which.

Cues
  • Whole architecture, one view
  • Top to bottom, five layers
  • A request travels one direction
  • Frame: who may talk to whom
0:200:18

1 · Browser

At the top is the browser. A single-page application holding no business logic and no database access of its own — it renders state and it collects intent. It addresses one origin, and only one. It never speaks to an individual service, which means anything below this line can change without a frontend release.

Cues
  • SPA — no logic, no database
  • Renders state, collects intent
  • One origin only
  • So anything below can change freely
0:380:27

2 · Gateway

Everything enters through the gateway, which is the only component in the system with a public address. It terminates TLS, verifies the token, applies rate limiting, and routes each request to the one service that owns it. What it deliberately does not do is authorise. It establishes identity and passes that inward; what you are permitted to do is decided by the service that owns the action, where the rules actually live.

Cues
  • The only public address
  • TLS, token, rate limit, route
  • Authenticates — does not authorise
  • Permission decided where the rules live
1:050:43

3 · Services

The third layer carries all of the business meaning — eight services, divided by domain rather than by technical function. Platform holds identity and audit. Market holds instruments, prices and derived series. Simulation, calibration and path generation. Trading, the strategies and the ordered record of what was executed. ML, the model registry and the feature store. Risk, stress testing and the topological pipeline. Explainability, attribution and narration. And Dashboard, the read models, the alert rules, and every open client connection.

Each of these is independently deployable and independently scalable, and none of them reaches into another's data. A service either calls a published API, or it reacts to an event.

Cues
  • Eight services — split by domain, not function
  • Platform · identity, audit
  • Market · prices, derived series
  • Simulation · calibration, paths
  • Trading · strategies, ordered record
  • ML · registry, feature store
  • Risk · stress, topology
  • Explainability · attribution, narration
  • Dashboard · read models, alerts, connections
  • Independently deployable and scalable
  • Never another's data — API or event
1:480:26

4 · Kafka

Which brings us to the fourth layer. Kafka sits beside the request path rather than beneath it, and that placement is the point — it is how services tell one another that something has happened, not a hop a user's request passes through on its way to data. The arrow runs both ways because every service both publishes and consumes. Delivery is at-least-once, so every consumer is built to be idempotent.

Cues
  • Beside the request path, not beneath
  • How services say something happened
  • Not a hop on the way to data
  • Arrow both ways — all publish and consume
  • At-least-once → consumers idempotent
2:140:23

5 · Storage

At the bottom is storage, in three tiers: Postgres with TimescaleDB for operational and time-series data, Redis for caching and job state, and object storage for large, write-once artefacts. This layer is partitioned by owner. Each service holds credentials to its own database and to nothing else — so there are no cross-service joins and no shared tables anywhere in the system.

Cues
  • Postgres + TimescaleDB · operational, time-series
  • Redis · cache, job state
  • Object store · large, write-once
  • Partitioned by owner
  • Own credentials only — no joins, no shared tables
2:370:15

Close

And the dashed line up the right-hand side closes the loop — Dashboard pushes state back to the browser rather than the client polling for it. One way in, one owner per capability, one store per owner.

Cues
  • Dashed line — Dashboard pushes to browser
  • Pushed, not polled
  • Land it: one way in, one owner per capability, one store per owner
