# QuantSim CI/CD: team guide

How our code gets from a laptop to the live site, and what each of us does along the way.
Read this once before your first pull request. The full technical reference is
[`docs/ci-cd.md`](ci-cd.md); the Jenkins setup is in [`ci/jenkins/README.md`](../ci/jenkins/README.md).

## 1. The big picture

```
 your branch ──PR──▶ develop ──PR──▶ test ──PR──▶ acceptance ──PR──▶ main
 (checks only)        DEV            TEST         ACC                PROD
                      built here     same build   same build         same build
                                                  + sign-off         + approval
                                                                     + version tag
```

- **Jenkins** is the robot that checks, builds and deploys. It runs in Docker on one team
  member's laptop at a time (section 5).
- **Every change goes through a pull request (PR).** Jenkins checks it; you merge only when
  it is green.
- **The app is built once, on `develop`.** Promoting to TEST, ACC and PROD reuses that
  exact build, so what was tested is what goes live.
- **Each step needs the one before it.** TEST needs DEV to have passed, ACC needs TEST,
  PROD needs an approver's sign-off on ACC.

## 2. The environments

| Environment | Branch | Website | Backend (API, database) |
|---|---|---|---|
| DEV | `develop` | https://develop.quantsim-4hz.pages.dev | On the laptop hosting Jenkins, `http://localhost:8081/api/platform/health` |
| TEST | `test` | https://test.quantsim-4hz.pages.dev | On the laptop hosting Jenkins, `http://localhost:8082/api/platform/health` |
| ACC | `acceptance` | https://acceptance.quantsim-4hz.pages.dev | On the laptop hosting Jenkins, `http://localhost:8083/api/platform/health` |
| PROD | `main` | https://quantsim-4hz.pages.dev | On the laptop hosting Jenkins, `http://localhost:8084/api/platform/health` |

The websites are on Cloudflare Pages and stay up even when every laptop is off. Backend
services (the platform API with PostgreSQL + TimescaleDB, Redis and Redpanda) run in Docker
on the laptop hosting Jenkins, one separate stack with its own databases per environment,
so they are up only while someone hosts. ACC and PROD stay there until the team decides to
move them to a dedicated server.

Databases do not move with a hand-over (section 5): the next host starts DEV and TEST with
fresh databases, and ACC and PROD get fresh databases on their next deploy. Each
environment's first admin comes from its encrypted secrets.

**How each environment deploys:**
- **DEV** and **TEST** always deploy by themselves: DEV on every merge into `develop`, TEST on
  every merge of a `develop → test` promotion PR.
- **ACC** and **PROD** deploy on merge too, but then wait for an approver in Jenkins, unless
  `AUTO_APPROVE=true` is set for that environment (section 7).

**Accounts and email in each environment:**
- People sign up on the website. Viewers can sign in once they open the emailed link; Quant
  and Analyst accounts also wait until an admin presses Approve on the Users page.
- DEV and TEST never send real email. Every email (verification, password reset,
  invitation, approval) lands in that environment's **Mailpit** inbox on the Jenkins host:
  http://localhost:8025 for DEV and http://localhost:8026 for TEST. Open it there to click
  the links.
- DEV and TEST also have four test accounts, re-created on every deploy: `test.admin`,
  `test.quant`, `test.analyst` and `test.viewer`. Their password is in the encrypted
  secrets (`TEST_USERS_PASSWORD`); ask Ali.
- ACC and PROD send real email through Gmail as `alimazhar+QuantSim@gmail.com` once the
  sending account is configured (`SMTP_USERNAME` in the env file, `SMTP_PASSWORD` in the
  secrets). Until then their emails wait in the queue and go out once it is set.

Other branches:
- `develop-poc`: the original proof of concept, frozen. **Never touch it.**
- `master`: empty. **Never touch it.**

## 3. Your everyday workflow

1. **Start from the latest `develop`:**
   ```bash
   git switch develop && git pull
   git switch -c feature/<short-name>      # bugfix/<short-name> for a fix
   ```
2. **Commit** with one plain line, no punctuation, for example
   `Add the price chart to the dashboard`. No "Co-Authored-By" or "Generated by" lines.
3. **Check before you push:**
   ```bash
   .claude/skills/quantsim-git-flow/scripts/preflight.sh
   ```
   It runs the same checks Jenkins will (lint, types, tests for the parts you changed) and
   checks your branch name and commit messages. Push only when it says
   `all checks passed`. On Windows the frontend part can take a very long time the first
   time (installing npm packages into a folder shared with Docker is slow); if it seems
   stuck, stop it with Ctrl+C and let the Jenkins check on your PR do that part.
4. **Push and open a PR into `develop`:**
   ```bash
   git push -u origin feature/<short-name>
   .claude/skills/quantsim-git-flow/scripts/pr.sh
   ```
5. **Wait for the Jenkins check** on the PR (a few minutes). Click **Details** to see the
   log in Jenkins.
6. **Merge** with **Create a merge commit** once it is green. Never squash or rebase; the
   merge commit keeps every commit and its author, which the FYP marking looks at.
7. **Jenkins deploys DEV automatically** a few minutes later. Check
   https://develop.quantsim-4hz.pages.dev.

Never push straight to `develop`, `test`, `acceptance` or `main`. GitHub cannot block it on
our free plan, so it is up to us.

## 4. What Jenkins checks

| Check | What it does | Runs when |
|---|---|---|
| Pipeline scripts | ShellCheck on `ci/scripts/` | every build |
| Frontend CI | `npm ci`, oxlint, TypeScript, Vitest with coverage, Vite build | every build |
| Backend CI | per service and library: ruff, formatting, mypy, pytest | when `services/` or `libs/` exist |
| Migration check | each service's database migrations up, down and up again on an empty database | services with migrations |
| Build images | builds a Docker image for each part whose code changed | `develop`, `hotfix/*` |
| Deploy + smoke test | deploys, then checks the site serves exactly the build that was deployed | environment branches |
| Sweep | removes leftover test containers and volumes, and old build cache | every build |

A PR build runs the checks only. Deploying happens after the merge, in the job for that
branch (Jenkins → `quantsim` → `develop`, `test`, ...).

The **Vercel** checks you also see on PRs are preview deployments from a separate
integration. They are not part of this pipeline and do not block anything.

## 5. Hosting Jenkins: taking turns

Jenkins runs on one laptop at a time. Whoever hosts it builds and deploys for the whole
team; everyone else just pushes.

```bash
ci/jenkins/host.sh status    # who is hosting, and the Jenkins link
ci/jenkins/host.sh start     # host Jenkins on your laptop
ci/jenkins/host.sh stop      # hand it over; ALWAYS run this before shutting down
```

How it works:
- `start` checks a shared "who is hosting" note (the **lease**) in our Cloudflare R2
  bucket and **refuses if someone else is hosting**. Then it downloads Jenkins' latest
  state (history, build numbers, releases for rollback), starts Jenkins, opens a free
  public link (`https://<random>.trycloudflare.com`) and redeploys DEV and TEST on your
  laptop.
- While you host, your laptop renews the lease every 2 minutes.
- `stop` uploads Jenkins' state to R2 and releases the lease, so the next person carries
  on exactly where you left off.
- The link changes on every `start`. `host.sh status` always shows the current one.

Rules:
- **Run `stop` before you close the laptop.** If you forget, the next person has to wait
  10 minutes for your lease to expire, or use `host.sh start --force`, which loses
  anything that changed on your laptop since your last `stop`.
- **Never start Jenkins with plain `docker compose up`.** It skips the lease, and two
  Jenkins at once would both deploy and tag releases.
- **When nobody hosts, nothing builds.** Pushes are picked up when the next person starts.

### One-time setup on your laptop
1. Install **Docker Desktop** and turn on **Start Docker Desktop when you sign in**. Keep at
   least 15 GB free on C:. Recommended, especially on a laptop short of disk or memory:
   - create `.wslconfig` in your Windows user folder (`%USERPROFILE%`) with:
     ```ini
     [wsl2]
     memory=10GB
     kernelCommandLine = sysctl.fs.aio-max-nr=1048576

     [experimental]
     autoMemoryReclaim=gradual
     ```
     It caps Docker's memory so Windows' page file does not grow to fill C:, and raises a
     Linux limit that Redpanda (the backend's message broker) runs into when DEV, TEST and
     test brokers run at once. Restart Docker Desktop afterwards.
   - if C: is tight, `powercfg /h off` in an administrator PowerShell removes the
     hibernation file (as big as your RAM); sleep still works.
2. Clone the repository and open **Git Bash** in it.
3. Get the `ci/jenkins/secrets/` folder from Ali over a private channel (password manager
   or encrypted zip, never chat or git) and copy it into `ci/jenkins/secrets/`.
4. Run once:
   ```bash
   ci/jenkins/init-env.sh
   ```
   It should end with `all secret files present`.
5. Try it: `ci/jenkins/host.sh start`, open the link, sign in, then `ci/jenkins/host.sh stop`.

## 7. Promoting a release

Promotions are pull requests between environment branches, always merged with
**Create a merge commit**. Agree in the group before promoting.

| Step | Command | Needs |
|---|---|---|
| DEV → TEST | `.claude/skills/quantsim-git-flow/scripts/pr.sh promote develop test` | `quantsim/dev-verified` on `develop` |
| TEST → ACC | `... pr.sh promote test acceptance` | `quantsim/test-verified` on `test` |
| ACC → PROD | `... pr.sh promote acceptance main` | `quantsim/acceptance-signoff` on `acceptance` |

`pr.sh promote` refuses if the required status is missing.

After merging:
- **TEST**: deploys and smoke tests by itself.
- **ACC**: deploys, then the `acceptance` job **waits for an approver**. Check the ACC site,
  then in Jenkins open `quantsim` → `acceptance` → the running build and click **Approve**
  (or **Abort** to reject).
- **PROD**: the `main` job **waits for an approver** before deploying. Click **Approve**;
  Jenkins deploys, smoke tests and tags the release `v<VERSION>` (from the `VERSION` file).
  Bump `VERSION` on `develop` before the next release, or the `main` build stops because
  that tag already exists.

If a deploy to ACC or PROD fails its smoke test, Jenkins **rolls back automatically** to
the last good release.

### Skipping the approval click (`AUTO_APPROVE`)
Each of `deploy/env/acc.env` and `deploy/env/prod.env` has a switch:

```ini
AUTO_APPROVE=false   # default: an approver clicks Approve in Jenkins
AUTO_APPROVE=true    # Jenkins signs off ACC / deploys PROD by itself
```

- Only the exact word `true` turns it on; anything else asks a person.
- Everything else still applies: the required status from the previous environment, the
  smoke test and automatic rollback. Only the click is skipped.
- Change it with a normal PR. Jenkins reads the file from the branch it builds, so the
  change counts once it has been promoted to `acceptance` (ACC) or `main` (PROD).
- With it on, GitHub shows the ACC sign-off as "Accepted automatically (AUTO_APPROVE)".

## 8. Hotfix: fixing PROD in a hurry

1. `git fetch && git switch -c hotfix/<short-name> origin/main`
2. Fix the problem and raise the patch number in `VERSION` (for example `0.1.0` → `0.1.1`).
3. Preflight, push, then `pr.sh` opens the PR into `main`. Jenkins checks and builds it.
4. Merge with **Create a merge commit**; approve production in Jenkins.
5. Bring the fix back: `pr.sh promote main develop`, merge with a merge commit.

## 9. Secrets

- Jenkins' credentials live in `ci/jenkins/secrets/` on the hosting laptop. They are
  git-ignored; **never commit them**, never paste them in chat.
- Each environment's app secrets (database passwords, signing keys) are encrypted in
  `deploy/secrets/<env>.enc.env` with SOPS. Jenkins decrypts them during a deploy.
- To edit them you need your own age key added to `.sops.yaml`; ask Ali.

## 10. When something goes wrong

| Problem | What to do |
|---|---|
| PR check is red | Click **Details**, read the log, fix on your branch and push again |
| `host.sh start` says someone is hosting | Ask them to run `host.sh stop`. If their laptop is off and it has been over 10 minutes, `start` works; `start --force` only if you are sure |
| Jenkins link does not open | `host.sh status` for the current link; it changes on every start |
| `host.sh start` ends with a `localhost` link | Cloudflare's tunnel service did not answer in time. Run `host.sh start` again; it keeps your running Jenkins and only fetches a new link |
| Can't sign in to Jenkins | Use an Incognito window; your browser may be filling in an old password |
| "Docker is not responding" | Start Docker Desktop normally (not "Run as administrator") and wait for **Engine running** |
| Builds fail with disk errors | Keep at least 5 GB free. Jenkins sweeps up after every build, but Docker's disk file on Windows only shrinks when compacted: `host.sh stop`, then in an administrator PowerShell `powershell -ExecutionPolicy Bypass -File ci\jenkins\compact-docker-disk.ps1`, then start Docker Desktop normally and `host.sh start` |
| Backend check says "test broker exited while starting" | The broker's own log is printed above the error. Usually memory or the async-IO limit: see the `.wslconfig` in section 5 |
| Deploy to ACC or PROD failed | Jenkins already rolled back. Read the log, fix on a branch, promote again |
| A site still shows the old version | Wait a minute and hard-refresh (Ctrl+F5); Cloudflare can take a moment |

## 11. Words you will see

| Term | Meaning |
|---|---|
| CI | Continuous integration: every change is checked automatically |
| CD | Continuous delivery: every passing change can be deployed with a click |
| Pipeline | The fixed series of steps Jenkins runs (section 4) |
| Promotion | Moving the same build to the next environment |
| Smoke test | A quick check after deploying that the site is up and serving the right build |
| Content hash | A fingerprint of a component's source; same hash means same build |
| Sign-off | An approver confirming ACC is good enough for production |
| Lease | The shared note saying which laptop hosts Jenkins |
