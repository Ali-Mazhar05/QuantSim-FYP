Figure B · service internals

Four layers, and one rule the network adds

On screen Figure B  ·  point at layer 4

Voiceover

Zooming into any one of the eight, this is what you find. Four layers: routes, application, domain, infrastructure. A layer calls only the layer beneath it, which is ordinary. The addition distributed operation forces is at the bottom — all outbound communication is confined to layer four. Domain code never opens an HTTP connection and never publishes to Kafka. It records an intent, and layer four turns that into a resilient call or a row in the outbox.

Two things follow. The resilience policy lives in one place per service instead of scattered through business logic. And the service is testable on its own, with nothing else running.

Figure B · the shared template

Nine releasable units, sixteen running deployments

On screen Figure B  ·  point at nothing — this beat is spoken

Voiceover

That layout is not written eight times. Every service is generated from one template, and the template carries the health and readiness endpoints, structured logging with correlation-id propagation, OpenTelemetry tracing, the outbox table and its drain, the resilient HTTP client, the idempotent Kafka consumer wrapper, the RBAC dependency, the Alembic setup, and the Dockerfile.

On deployment, be precise about the count. Nine releasable units — eight services and the gateway. Seven of the eight ship a worker beside their API, so sixteen deployments actually run. And those workers are not all the same animal: four are job workers, measured by queue depth and scaled on backlog; three are continuous — Market Data's scheduler, Trading's ordering engine, Dashboard's alert evaluator — measured by consumer lag and scaled by partition count. That is why they are never merged.

Figure C · the outbox

The failure that would corrupt everything, and the fix

Switch to Figure C  ·  point at the dashed transaction box, then the ack arrow

Voiceover

This is the mechanism I would defend hardest, because without it the whole event-driven design is wishful thinking. The subtlest failure in a system like this is the gap between “I committed my state” and “I published my event”. If a service commits and then dies before publishing, nothing downstream ever learns, the databases diverge permanently, and there is nothing to detect it. Two-phase commit across Postgres and Kafka is not available to us.

So every service writes its business rows and an outbox row in one local transaction — both or neither. A small drain worker then reads unpublished rows in id order, publishes them, and marks them published only after the broker acknowledges. A crash between publish and mark produces a duplicate, never a loss. And duplicates are already handled, because delivery is at-least-once and every consumer deduplicates on a business key. The hard problem becomes an easy one.

If you have time for one more sentence: the outbox is in the template, so all eight services have it whether their author thought about it or not.

Figure D · execution model

What happens between the click and the progress bar

Switch to Figure D  ·  walk steps 1 through 8 with the pointer

Voiceover

Concretely, a user starts a Monte Carlo run. The gateway verifies the token and routes to Simulation. Simulation validates, writes a job row in status queued, enqueues the id on its own Redis queue, and returns the job id immediately — the request is over in milliseconds. A CPU worker on a separate deployment claims the job under a lease, partitions the paths across its cores, and bulk-writes results.

Then the interesting part. The worker publishes progress through its outbox to Kafka. Dashboard consumes it, projects it into its own database, and pushes to the browser over a WebSocket. Simulation never talks to the browser — it announces facts and knows nothing about who is watching. That is why a Simulation redeploy does not drop a single live client connection, and why the same completion event can also wake Risk and Explainability without Simulation knowing they exist.

Every job carries an idempotency key derived from its parameters, so a caller that times out on submission can safely retry — it cannot produce two result sets.
2:100:25
Data

No joins — validate on write, project for read

Back to Figure A if it is one key away, otherwise stay on D

Voiceover

Eight databases means no foreign key ever crosses a service boundary, so we have one pattern for that and we apply it everywhere: validate on write, project for read, never join. Simulation checks an instrument exists by calling Market Data when the calibration is written, and keeps a small local reference projection for display.

The load-bearing case is the dashboard. If every widget fanned out to five services, a page load would multiply latency and couple its availability to all of them at once. Instead Dashboard subscribes to everyone's domain events and keeps its own query-shaped projections, so a widget read touches exactly one database — its own. The cost is bounded staleness, measured as event-to-projection lag, and these are analytical views that were reading precomputed aggregates anyway.

ML's feature store is the same pattern doing extra work: each value is stamped with the knowledge-time the event arrived, which makes look-ahead bias structurally impossible rather than merely discouraged.
2:350:25
Failure

Every call site names its fallback

Point at Figure B's third chip — the resilience list — if it is still on screen

Voiceover

Last thing. Because the network is an ordinary failure condition, every outbound call from layer four carries the same policy: a timeout always set, bounded retries with jittered backoff for idempotent operations only, a circuit breaker, a bulkhead bounding concurrency per dependency, and an explicit fallback. The rule that makes it coherent is that every call site must name its fallback. “Unavailable” is never allowed to mean hang or unhandled exception; it means a specific chosen degradation, written down and asserted in tests.

And where a workflow spans services, there is no distributed transaction — it is a choreographed saga with compensations. If a stress run's simulated market fails, Risk marks its own run failed and emits stress.failed. The invariant is not that three databases changed atomically. It is that no service ever shows a state implying another service's work succeeded when it did not.

Likely first questions
  • “Why not put the job queue on Kafka too?” Job semantics — claim, lease, retry, dead-letter, single consumer — and log semantics — durable ordered replay, many independent consumers, offsets — are different problems. Collapsing them loses one of the two.
  • “How does Trading stay strictly ordered?” Kafka partitions keyed by portfolio, one consumer per partition, consumers idempotent on (portfolio_id, seq). It scales by adding partitions, never by adding concurrency inside one.
  • “What if the LLM provider is down?” The XAI worker has a timeout, a breaker, and a cached-or-templated fallback — narration degrades, the explanation itself still returns.
  • “Can you rebuild it from nothing?” Terraform provisions the infrastructure and each service's Alembic history provisions its own schema, so no engineer's manual knowledge sits in the loop.
